12// Display device filter which reduces the amount of redundant background
13// re-drawing, for a collection of up to 15 designated background colors.
14//
15// A natural, most efficient way to avoid needless redrawing of identically
16// colored pixel content is to use a frame buffer that 'remembers' the last
17// color written for each of the device pixel. With such framebuffer, redundant
18// redraws are completely eliminated - an attempt to write a pixel with the same
19// color as previously, are silently discarded. Unfortunately, such a frame
20// buffer requires significant RAM, which microcontrollers will usually not have
21// enough to spare. For example, to buffer the contents of an ILI9486 display,
22// we need 480 x 320 x 2 (width x height x bytes per pixel) = 300 KB of RAM.
23//
24// This device filter uses a compromise, capable of achieving a very significant
25// reduction in redundant redraws, at a fraction of the memory footprint.
26// Specifically, it focuses on use cases in which large areas are getting
27// rect-filled using colors from a small palette. This is common in GUIs, that
28// use solid backgrounds and some amount of solid area fills using a predefined
29// set of colors. The device maintains a reduced-resolution framebuffer, whose
30// each pixel corresponds to a rectangular area of the underlying device. Each
31// pixel of the framebuffer can take one of 16 values. Values 1-15 mean that
32// the corresponding rectangle in the underlying device is known to be entirely
33// filled with the specific color from a 15-color palette. Value 0 means that
34// this is not the case; i.e. that the corresponding rectangle either isn't
35// known to be mono-color, or that it contains pixels with colors outside of
36// that small palette. When 'Fill-rect' is called on this filter, using a color
37// from the pre-specified 15-color palette, the implementation omits writes
38// to the areas that are already known to be filled with the given color.
39//
40// With 4x resolution along both X and Y axes, i.e. when each pixel of the
41// framebuffer corresponds to a 4x4 rectangle, we achieve 64-fold reduction in
42// the RAM footprint. For example, the frame buffer for the aforementioned
43// ILI9486 display now only uses 4800 bytes.
44//
45// This filter is meant to be used directly on top of a physical device. In
46// particular, it expects the underlying display output to have zero offset.
47// That is, the (0, 0) nibble of the background mask corresponds to the output
48// rectangle (0, 0, kBgFillOptimizerWindowSize - 1, kBgFillOptimizerWindowSize -
49// 1).
