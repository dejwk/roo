186// Primary top-level interface for drawing to screens, off-screen buffers,
187// or other devices. Supports rectangular clip regions, as well as arbitrary
188// clip masks.
189//
190// Able to render two types of objects:
191// * Objects implementing the Drawable interface. These are capable of
192// drawing themselves to a device.
193// * Objects implementing the template contract of a 'streamable'. These are
194// capable of generating a stream of colors, representing pixels corresponding
195// to a rectangular shape, row-order, top-to-bottom and left-to-right.
196// (Non-rectangular shapes can be provided by using transparency as a color.)
197//
198// The streamable contract is only implemented by some specific but important
199// types of drawable objects, such as images. The streamables have one important
200// benefit, which is the sole motivation for the existence of this interface:
201// two (or more) streamables, which may be partially overlapping, and which may
202// have transparency, can be rendered together to an underlying device, alpha-
203// blended when necessary, such that each pixel is only drawn once (i.e. no
204// flicker), but without using any additional memory buffers. An important use
205// case is rendering of kern pairs of font glyphs (e.g. AV) without using extra
206// buffers and yet without any flicker, which normally happens if glyphs are
207// drawn one after another.
208//
209// Note: streamable is a template contract, rather than a virtual method
210// contract, so that the code for overlaying the images can be optimized by the
211// compiler, and tuned to the specific types. It yields the best possible
212// performance, although it has a drawback of increasing program size. TODO: if
213// program sizes turn out to be a problem, it may be worth exploring virtual
214// version of this contract, using vector APIs (i.e., returning a large, e.g.
215// O(100), number of pixels from a single virtual call) which may be a good
216// balance between performance and program size.
